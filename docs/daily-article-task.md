# 毎日の記事自動作成の手順（自動実行用）

この手順は、毎日朝6時ごろ（日本時間）に起動する自動作業で使う。人の確認なしで公開まで行うため、品質と正確さを最優先にする。1回の実行で作る記事は1本だけ。

## 公開の方針（運営者の常時の指示）

- 運営者への確認は不要。問題がなければ、プルリクエストの作成・マージ・本番での表示確認まで、すべて自動で進める。「運営者に確認する」「運営者の承認を待つ」という手順は、この作業にはない。
- 運営者が「マージしない」「公開しない」と明示したときだけ止まる。
- 以下の「うまくいかないとき」は、客観的に公開できない場合（根拠を確認できない、ビルドやリンクチェックが通らないなど）の扱い。まず自分で直して再実行し、それでも直らない場合だけ、理由を記録して終了する（運営者には確認を求めない）。

## 1. 準備

1. リポジトリ uk-support1/fukushi-website-comparison の main を最新にし、`daily/YYYYMMDD`（日本時間の今日）ブランチを main から作る。
2. `docs/blog-writing-guide.md`（書式・編集方針・予約投稿・カバー画像）を読む。
3. `docs/blog-topic-queue.md` の最初の未着手（`- [ ]`）テーマを選ぶ。
4. `content/blog/` の既存記事と、`docs/partner-blog-topics.md`（福祉ITパートナーのブログ一覧）を確認し、テーマ・切り口・タイトルが重なる場合はそのテーマを「- [x]（重複のため見送り）」にして次のテーマにする。
   - 可能なら https://fukushi-it-partner.com/sitemap.xml から一覧を取り直して `docs/partner-blog-topics.md` を更新する。

## 2. 調査

- WebSearch で、厚生労働省・こども家庭庁・警察庁・IPA・個人情報保護委員会・WAM NET・都道府県などの公的情報を優先して確認する。
- 数字・制度の要件・施行時期など、確認できなかったことは書かない（または「自治体に確認」と明記する）。
- 出典に載せるURLは、実際に開けること（HTTP 200）を確認したものだけにする。開けないものは載せない。

## 3. 執筆（content/blog/<スラッグ>.md）

- 書式は既存記事にならう。必須：title、description、category、date（日本時間の今日）、cover（`{"catch": "短い見出し／改行位置", "sub": "補足"}`）、lead、summary、related（既存記事のスラッグ3つ）、faq（3問）、sources。
- 本文は3,000〜5,000字程度。見出し（##）4〜7個、表やチェックリスト、囲みボックスを使って読みやすく。
- 対象読者は福祉事業所の運営者・担当者。記事の中で特定の制作会社（福祉ITパートナーを含む）を「おすすめ」と推すことはしない。比較記事・既存記事へのリンクは、下の「比較記事への誘導（必須）」にしたがって入れる。
- 福祉ITパートナーのブログ記事の構成・文章を参考にしたり流用したりしない。
- 誇張・断定（「必ず」「No.1」など）や、根拠のない数字は使わない。

### 比較記事への誘導（運営者の指示。必須）

お役立ち記事の大きな目的は、読者に**比較記事（`/comparisons/…`）を開いてもらうこと**。どの記事にも、記事の内容に合わせた誘導を、次の2か所に入れる。文面は記事ごとに考え、他の記事の使い回しにしない。

1. **記事の途中**：2つ目の `##` 見出しの前に、`:::point タイトル` の囲みボックスを置く。
2. **記事の終わり**：まとめの後に、`:::info タイトル` の囲みボックスを置く。

書き方の決まり：

- 誘導先は、その記事のテーマにいちばん近い比較記事（`welfare` `group-home` `b-type` `a-type` `shuro-iko` `houkago-day` `jihatsu` `seikatsu-kaigo` `soudan-shien`）。種別が特定できない記事は福祉事業所向け（`welfare`）。リンクは `[ラベル](/comparisons/<スラッグ>-comparison.html)` の形で書く。
- 各ボックスは「読者の状況・疑問に触れる一文 → 比較記事を見ると何がわかるか → 目立つリンク行」の順にする。リンク行は、ボックスの最後に `- **[<比較記事のタイトル>を見る ›](/comparisons/….html)**` と独立した行で置く（文中のリンクとは別に付ける）。
- 比較記事に載っていることだけを書く。比較記事にない項目（例：SEO設定、バックアップ、マップ対応は福祉事業所向けの比較にはない）を「比較で確認できる」とは書かない。「必ず」「最適な会社がわかる」などの断定もしない。
- ボックスのタイトルは、記事ごとに違う、読者の「次の行動」を促す言い方にする（例：「開所日から逆算して、依頼先を絞りましょう」）。
- テーマが合う場合に限り、福祉ITパートナーのページ（`https://fukushi-it-partner.com/…`）へのリンクを、比較記事のリンクのあとに添えてよい。リンク先の内容に合う案内にし、**同じボックス内に「※福祉ITパートナーは、当サイトの運営者の関連会社です。」を必ず書く**。比較記事のリンクを置き換えるのではなく、あくまで追加とする。

例（記事の途中）：

```
:::point 相場を知ったら、実際の会社の料金も見てみましょう
相場と実際の料金には開きがあることもあります。福祉事業所向けのサービスについて、公式サイトで確認した1年間の費用の目安を、[比較記事](/comparisons/welfare-comparison.html)で見られます。

- **[福祉事業所向けホームページ制作会社比較を見る ›](/comparisons/welfare-comparison.html)**
:::
```

## 4. 生成と確認

1. `node scripts/make-blog-covers.cjs`（新しい記事のカバー画像を生成）
2. `node scripts/build-blog.cjs`
3. `node scripts/check-links.cjs .`（bad 0 であること）と `node scripts/check-blog-cta.cjs`（ng 0 であること。比較記事への誘導が前半と終盤に入っているかの確認）
4. 生成されたカバー画像を目で確認し、見出しが不自然に改行されていれば cover.catch の「／」位置を直して `--force` で作り直す。
5. `docs/blog-topic-queue.md` の該当テーマを `- [x]` にし、末尾に「（YYYY-MM-DD 公開: <スラッグ>）」を書く。

## 5. 公開

1. コミットメッセージは日本語で「お役立ち記事を追加：<タイトル>」。
2. `daily/YYYYMMDD` を push し、main へのプルリクエストを作成（本文に記事タイトル、出典、確認結果を日本語で書く）。
3. プルリクエストをマージする（運営者から「確認なしでマージしてよい」と許可を得ている）。
4. 数分後に https://fukushi-hp-hikaku.com/blog/<スラッグ>/ が表示されることを確認する。GitHub Pages の公開処理がタイムアウトで失敗していたら、Actions の該当実行を再実行する。

### プルリクエスト用のツールがない場合

GitHub のプルリクエスト作成・マージのツール（mcp__github__*）が使えない環境では、次の方法で公開する（運営者の許可あり）。

1. `daily/YYYYMMDD` ブランチを push して記録を残す（失敗しても続行してよい）。
2. `git fetch origin main && git checkout main && git reset --hard origin/main` で最新の main にする。
3. `git merge --no-ff daily/YYYYMMDD -m "<コミットメッセージと同じ内容>"` でマージする。
4. `node scripts/build-blog.cjs` と `node scripts/check-links.cjs .` をもう一度実行し、生成物に差分があればコミットする。
5. `git push origin main` で公開する。push が拒否された場合は無理に回避せず、状況を報告して終了する。

## うまくいかないとき

- 調査で十分な根拠が得られない、ビルドやリンクチェックが通らない場合は、まず原因を直して再実行する。それでも直らない場合だけ、公開せずにプルリクエストを下書きのまま残し、理由を本文に書いて終了する。
- 既存の記事・比較ページ・デザインは変更しない（この作業は記事を1本追加するだけ）。
