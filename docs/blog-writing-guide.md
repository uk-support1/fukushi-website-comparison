# お役立ち記事（ブログ）の追加・更新手順

## 仕組み

- 記事の原稿は `content/blog/<スラッグ>.md`。ファイル名がURLになる（`/blog/<スラッグ>/`）。
- `node scripts/build-blog.cjs` で次を生成する。生成物もコミットする（公開時にNodeは不要）。
  - `blog/` 以下の記事・一覧・カテゴリーページ
  - `about/index.html`（原稿は `content/about.md`）
  - `sitemap.xml`（既存の比較ページを含むサイト全体）
  - トップページの新着記事（`index.html` の `<!-- BLOG:LATEST -->` 部分）
- `blog/` は毎回作り直すため、直接編集しない。
- 共通ヘッダー・フッター・GA4タグはスクリプト内で生成（GA4タグは `assets/data/b-type-content.json` の `analytics` を流用）。

## 原稿の書式

先頭に `---json` と `---` で囲んだメタ情報（JSON）、その後に本文（Markdown）を書く。

| キー | 必須 | 内容 |
| --- | --- | --- |
| title | ○ | 記事タイトル（32〜45文字程度。検索語を前半に） |
| description | ○ | 検索結果の説明文（80〜120文字程度） |
| category | ○ | `fukushi-kiso` / `security` / `hp-seisaku` / `unei` |
| date | ○ | 公開日 `YYYY-MM-DD` |
| updated | | 更新日。内容を見直したら必ず更新する |
| lead | | 導入文 |
| summary | | 「この記事でわかること」（配列） |
| related | | 関連記事のスラッグ（配列）。存在しないとビルドエラー |
| faq | | `{ "q": "...", "a": "..." }` の配列 |
| sources | | `{ "title": "...", "url": "...", "note": "任意" }` の配列 |
| draft | | `true` にすると公開しない |

本文で使える記法：`##` / `###` 見出し（`##` が目次になる）、段落、`- ` 箇条書き、`1. ` 番号付き、表（`| a | b |`）、`>` 引用、`**強調**`、`[文字](URL)`。サイト内リンクは `/blog/xxx/` のように `/` 始まりで書くと相対パスに変換される。囲みボックスは次のとおり（point/warn/check/info）。

```
:::point タイトル（省略可）
本文
:::
```

## 編集方針（品質・SEO）

- 1記事1テーマ。検索する人の疑問に答え切る。記事数のための薄い記事は作らない（Googleの「大量生成コンテンツの不正使用」ポリシーに抵触するおそれ）。
- 制度・統計・法令は公的機関の一次資料を優先し、`sources` に出典を必ず記載。確認できない事項は書かない、または「〜とされている」「自治体に確認」と明記。
- 料金・制度は時点を明記。改定があったら `updated` を更新して見直す。
- 特定の制作会社を推す表現は避け、比較記事への導線は中立的に。広告・提携による掲載をする場合は「広告」「PR」を明示する（景品表示法のステルスマーケティング規制）。
- 追加後は `node scripts/build-blog.cjs` を実行し、生成物をまとめてコミットする。

## 掲載企業のブログとの重複を避ける（独立した立場で書く）

- 本サイトの記事は、掲載企業（福祉ITパートナーを含む）から独立した編集部の立場で書く。
- 掲載企業のブログ記事を下敷きにしたり、構成・見出し・文章を流用したりしない。同じテーマを扱う場合も、切り口（比較・チェックリスト・制度の一次資料の解説など）を変え、本文は独自に書く。
- 掲載企業の記事を出典にする場合は、他の情報源（公的機関・報道・他社）と並べて使い、そのページだけに依拠しない。
- 新しい記事を書く前に、下の一覧とテーマ・タイトルが重ならないか確認する。一覧は分かり次第追記する。
